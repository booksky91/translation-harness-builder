# 프로젝트 고유 지식 문서의 생성 청사진

**용도:** 용어·인물·스토리·도메인·매체 정보의 필수 레코드, 적용 조건, 근거, 예외, 인덱스 연결을 정의한다. 기존 사용자 작성 내용은 보존하고 누락된 필드를 보완한다. 원본을 확인하지 않은 인명·시간·사건·독음·정책 결정은 확정하지 않으며, 미확정 사유와 검증 항목을 남긴다.

## 목차
1. 지식 자산의 공통 레코드 계약
2. `glossary/GLOSSARY.md`
3. `characters/CHARACTER_BIBLE.md`
4. `characters/profiles/<id>.md`
5. `story/STORY_BIBLE.md`
6. `story/arcs/<id>.md`
7. `story/FILE_INDEX.md`
8. `story/TIMELINE_AND_REVEALS.md`
9. `knowledge/DOMAIN_BIBLE.md` 및 주제별 상세
10. `media/UI_CONTEXT.md`
11. `media/SUBTITLE_CONSTRAINTS.md`
12. 프로젝트 유형별 생성 조합과 완료 조건

## 1. 공통 레코드 계약

인물·루트·용어·제품 개념의 모든 상세 자산은 아래 정보를 표현할 수 있어야 한다.

| 필드 | 질문 | 필수성/관리 방법 |
|---|---|---|
| `record_id` | 이 사실/규칙을 안정적으로 참조하는 ID는? | 필수; 문서 이동 후에도 유지 |
| `record_type` | 사실, 인물 화법, 용어, 사건, 화면, 기술 제약 중 무엇인가? | 필수 |
| `scope` | 어떤 파일·장면·제품 버전·로캘·화자·수신자에서 적용되는가? | 필수; 전역이면 이유 명시 |
| `source_refs` | 원문에서 직접 본 정확한 위치는? | 사실 주장에는 필수; 없으면 `UNVERIFIED` |
| `observed` | 원본을 읽고 실제로 확인한 문구·동작은? | 추론과 분리 |
| `context_confirmed` | 앞뒤 장면·제품 흐름으로 확인한 조건은? | 확인했을 때만 기재 |
| `inference` | 원문에 직접 쓰지 않은 해석은? | 해당 시 명시, 전역 금지 |
| `translation_effect` | 번역어/호칭/문체/누락 금지 정보가 어떻게 달라지는가? | 실용적인 자산에서 필수 |
| `exceptions` | 어떤 상황에서는 규칙을 적용하면 안 되는가? | 조건부 사실이면 필수 |
| `proposal` | 현재 목표 언어 표현 후보는? | 후보를 사실로 둔갑시키지 않음 |
| `approval` | 승인 여부, 승인자·일자·적용 범위는? | 승인되지 않으면 `UNAPPROVED` |
| `runtime_state` | 실제 매체 실행 확인은? | 별도; 기본 `NOT_TESTED` |
| `linked_records` | 연결된 인물/스토리/용어/이슈 ID는? | 해당될 때 상대 링크 사용 |

**최소 한 규칙 = 적용 조건 + 근거 + 번역 영향 + 반례/미확정.** 성격·세계관 소개 같은 단순 수식어만으로 규칙을 만들지 않는다. 문서마다 고유하게 변하는 정보와 공통 정책을 구별한다.

## 2. `glossary/GLOSSARY.md` — 원문 표현과 목표 표현의 관계

### 언제 생성할까

기본 문서다. 시작 시 인명·전문용어가 하나도 확인되지 않았어도 **용어 등록 규칙/표 구성/상태**는 제공한다. 의미 있는 항목은 원본에 직접 등장하고 반복적으로 표기 판단이 필요할 때 등록한다.

### 정확한 섹션 청사진

```md
# Project Glossary

## 0. 이 용어집의 유효 범위와 상태
- 대상 언어쌍/로캘, 소스 버전, 승인의 현재 유효성
- 승인된 표기와 단순 기준안 구분

## 1. 등록·정규화·적용 규칙
- 무엇을 표제어로 등록하는가
- 동일 개념의 원문 변형/활용/호칭/독음의 취급
- 전체 문자열 치환을 허용하지 않는 조건
- 일반 명사·임의 호칭은 어디에서 관리하는가

## 2. 항목 검색 인덱스
| term_id | concept_id | 원문 표면형 | 목표 언어 표기/후보 | 분류 | 상태 | 조건 | 상세 앵커 |

## 3. 인물·지명·기관·브랜드
[해당 원문이 확인되면 term_id별 기록]

## 4. 세계관·제품·전문기술·시스템 용어
[해당 원문이 확인되면 term_id별 기록]

## 5. 별명·친밀 호칭·관계 조건부 어휘
[해당 원문이 확인되면 term_id별 기록]

## 6. 독음·루비·의도적 표기 변형
[사실로 확인된 위치와 관련 term_id]

## 7. 미확정 용어·동형이의어·충돌
| issue_id | term_id | 문제 | 검증할 원문 | 다음 담당 |

## 8. 출처/결정/변경 참조
- operations/SOURCES.md와 DECISIONS.md 연결
```

### 각 용어 상세 항목의 표준 구성

```md
<a id="term-t001"></a>
### T001 — [개념명 또는 원문 표면형]
- 지칭 개념 ID: CONCEPT-...
- 원문 표면형: [원문 그대로]
- 원문 변형/별칭/읽기: [동일 개념인지 구분하여]
- 의미/실체: [원문에서 확인된 범위]
- 목표어 후보: [미확정이면 `UNKNOWN`]
- 상태: UNVERIFIED | DRAFT | APPROVED
- 적용 범위: [프로젝트 버전/장면/화자/수신자/공개 시점]
- 이 규칙을 쓰지 않을 때: [다른 실체/의도적 표기 변형/말장난]
- 근거: [source_id / unit_id / 위치]
- 연결: [인물/스토리/기술 상세 앵커]
- 결정: [DECISION-ID 또는 `없음`]
- 업데이트 조건: [독음/공식 표기/새 장면 확인 시]
```

**관리 원칙:** (a) 하나의 개념은 기본적으로 하나의 `concept_id`를 둔다. (b) 표현 변형이 캐릭터·서사 기능을 갖는 경우 별도 `term_id`를 두되 지칭 실체는 연결한다. (c) `같은 소리`가 같은 인물임을 증명하지 않는다. (d) 미승인 후보를 전체 치환 규칙으로 사용하지 않는다. (e) 이름/직함/애칭이 알려진 시점 이후에만 사용되는 경우 공개 조건을 기록한다.

## 3. `characters/CHARACTER_BIBLE.md` — **캐릭터 상세의 탐색 인덱스**

### 책임

**누가 어디에 기록되어 있는가**, 어떤 관계별 절을 열어야 하는가를 알려준다. 여기 있는 한 줄 보이스 요약만으로 번역을 확정하지 않는다. 직접 열어야 하는 상세 파일/앵커로 연결한다.

```md
# Character Bible — 화자·관계 탐색 인덱스

## 0. 사용 순서와 사실/번역안 분리
1. 실제 원문에서 화자, 수신자, 장면/관계 단계 확인
2. 아래 인덱스에서 화자 상세 파일로 이동
3. 해당 상대/시점의 개별 규칙 절까지 읽기
4. glossary의 호칭/별명과 현재 장면 원문 대조

## 1. 인물 탐색 인덱스
| character_id | 원문 화자 표기/별칭 | 인물명·독음 상태 | 상세 프로필 | 관계별 절 | 조사 상태 |

## 2. 공통 관계/호칭 판정 원칙
- 실제 대화 상대를 확인하지 못했을 때의 제한
- 호칭/친밀도/직책/호감과 친족 관계 오인 방지

## 3. 방향성 있는 관계별 빠른 인덱스
| 화자→수신자 | 시점/관계 단계 | 확인된 원문 호칭 | 상세 앵커 | 검증 상태 |

## 4. 부적절한 일반화/대표적 위험
- 이 인물은 언제나 반말이라는 단정, 모든 루트 관계 통합 등

## 5. 적용 기록과 QA
- work unit에 남겨야 하는 character_id/relationship_record_id

## 6. 미확정 인물·관계 및 업데이트
| ID | 불확정 내용 | 필요한 원문/문맥 | 이슈 |
```

**방향성:** `A→B`와 `B→A`는 다른 규칙이다. 캐릭터 둘 사이에 친밀도가 존재해도 화자에 따른 존대·애칭·연기·지위는 다를 수 있다. 인덱스에서 한 쌍을 가리키더라도 양방향 규칙을 합치지 않는다.

### 인덱스와 상세 분리 기준

- 여러 상대가 있는 인물 → 인물별 상세 하나를 두고, 그 안에 상대별 **앵커**를 둔다.
- 특정 장면에서만 발생한 예외 → 일반 보이스가 아니라 상대별 예외/장면 절에 기록한다.
- 아직 직접 확인된 발화가 없는 이름만 등장 → `CHARACTER_BIBLE`의 미조사 목록에 남기고 빈 프로필 남발 금지.

## 4. `characters/profiles/<character-id>.md` — 인물 실무 카드

**실제 작성해야 하는 항목을 생략하지 마라.** 인물 소개만 쓰면 번역용 카드로 미완성이다.

```md
# [캐릭터 표제명] — Voice/Relationship Profile ([character_id])

## A. 식별과 등장 범위

## B. 원문에 확인되는 역할·배경과 해석

| 요소 | 원문에서 확인된 표현·예 | 목표 언어 기본 후보 | 적용 조건 | 근거·상태 |
| 문장 길이/리듬 | ... | ... | ... | ... |
| 높임법/말끝 | ... | ... | ... | ... |
| 어휘/말버릇 | ... | ... | ... | ... |
| 인칭/주어 생략 | ... | ... | ... | ... |
| 감정 강도/침묵 | ... | ... | ... | ... |

## D. 방향별 관계/호칭 규칙 (상대별 앵커 필수)
<a id="char-c001-to-c002-stage1"></a>
### C001 → C002 / 관계 단계 1
- 수신자 식별 근거: [직접 호명/행동/상호 발화/추정]

## E. 관계 변화·예외 트리거
| 트리거/장면 | 이전 규칙 | 전환 규칙 | 종료 조건 | 출처 | 확정 여부 |

## F. 시점/루트/서술자 주의
- 다른 루트 지식의 무단 유입 금지
- 본인의 대사와 본인 1인칭 서술 구별

## G. 실제 대사 사례와 QA

## H. 충돌·보류·승인·변경
- 해당 이슈 ID, 검토자/승인자, 전역 적용 금지 범위, 관련 상세 링크
```

### 인물 카드의 엄격한 작성 규칙

- **화자–수신자–시점–목적을 동시에 확인**한다. 직전 대사가 특정인 대사였다는 이유만으로 수신자를 그 인물로 확정하지 않는다.
- 기본 보이스는 기본값이고 강행 규칙이 아니다. 농담 존대, 위협, 회상, 공적 발표 등에서는 **조건별 변형**을 기록한다.
- `원문에서 말끝이 높다`와 `목표 언어에서 존댓말을 쓴다`는 동일한 사실이 아니다. 관찰/번역 제안을 분리한다.
- 누구나 쓰는 일반 인칭/호칭을 인물 고유 애칭으로 확정하지 않는다.
- 배경/성격이 200자라도 특정 수신자별 규칙이 없으면 그 사실을 명시하고 `말투 미확정`으로 둔다.
- 동명이인·독음 미확정 인물은 별도 ID와 `identity_unverified`로 관리한다. 추측으로 병합하지 않는다.

## 5. `story/STORY_BIBLE.md` — 서사·장면·분기 탐색 인덱스

```md
# Story Bible — 장면/루트/시점 인덱스

## 0. 사용 방법
- 현재 원문 파일/장면/분기 상태 식별 → 상세 파일 읽기 → 노출 가능 정보 확인

## 1. 이야기 세계의 확인된 사실과 불확실한 가설
- 사실(출처 포함) / 인물의 주장·소문 / 번역자가 추정한 모델 구별

## 2. 시나리오 계열·루트/장면 인덱스
| arc_id | 원문 파일/범위/식별자 | 주요 시점·화자 | 분기 전제 | 상세 파일 | 검증 상태 |

## 3. 시간·지식 공개 인덱스
| 정보 ID | 누가 언제 알게 됨 | 독자가 알게 되는 시점 | 상세 링크 | 위험 |

## 4. 서술자·시점 변경 인덱스
| 장면/단위 | 화자/서술자 | 확인 근거 | 혼동 위험 |

## 5. 루트별 상충/세계관 병합 금지
- 이름 유사/후기 설정/특수 루트 정보가 공통 사실인지 확인 여부

## 6. 파일 매핑·타임라인 자료로 이동
- FILE_INDEX, TIMELINE_AND_REVEALS, arcs 문서 링크

## 7. 아직 입증되지 않은 이야기 연결과 검증 과제
```

**상위 바이블에 모든 스토리의 줄거리 전체를 복사하지 않는다.** 주요 이야기 사실을 아주 짧게 적어도 반드시 그 사실을 확인할 수 있는 하위 상세 링크를 가리켜야 한다.

## 6. `story/arcs/<arc-id>.md` — 장면군/루트의 번역 맥락 카드

이 문서는 `챕터 줄거리`가 아니라 **번역에서 어떤 정보를 알고, 어떤 정보를 아직 모르는가**를 결정하는 기록이다.

```md
# [장면군/루트명] — ARC-001
[STORY_BIBLE로 돌아가기](../STORY_BIBLE.md)

## A. 적용 범위와 원본 매핑
- arc_id, 원문 파일 패턴, unit 범위, 분기 상태, 접근한 소스/버전

## B. 시작 시점과 선행 조건
- 당시 시간/장소/인물/관계 단계, 확인된 것과 추정된 것

## C. 주요 사건 연결 — 순서 확신도와 함께
| event_id | 사건 | 원문 단위 | 선행 조건 | 관찰/소문/추정/확정 |

## D. 인물별 지식과 정보 공개 시점
| scene_id | 정보 | 누가 아는가 | 누가 모르는가 | 독자에게 보였는가 | 최초 확인 unit |

## E. 시점·서술자·관계 변화
| scene_id | narrator | speaker | relationship_stage | 위험한 번역 선택 |

## F. 분기·병렬 장면·선택지 연결
- 선택지의 의미, 진입 조건, 결과 확인 여부, 루트간 상호 배제

## G. 번역에 직접 영향을 주는 조건
- 호칭 변화, 소문→사실 여부, 시간 표현, 중의성, 비밀을 드러내는 단어

## H. 고위험 / 전역 일반화 금지
- 미래 지식 소급, 병렬장면 연속 발생 오인, 뒤 시점 이름 사용 금지

## I. 실제 원문 단위 근거
| unit_id | 사건/발언 | 해석의 범위 | 참조할 인물/용어 |

## J. 보류·충돌과 변경 이력
- 타임라인 불확실성, 관련 ISSUE/DECISION, 다음 확인할 데이터
```

**결론·반전 관리:** 번역자가 결말을 아는 것은 캐릭터가 그 시점에 아는 것과 다르다. 인물, 플레이어, 서술자, 번역자는 별도 지식 주체로 관리한다. 후속 루트에서 확인된 호칭/정체를 앞부분에 자동 적용하지 않는다.

## 7. `story/FILE_INDEX.md` — 물리 파일과 논리 장면의 매핑

파일 단위와 장면/에피소드가 1:1이 아니거나 원본의 정렬 순서가 실행 순서가 아닐 때 생성한다.

```md
# Source File / Story Segment Map

## 파일-장면 대응표
| source_path | version | unit_range | scene_id | arc_id | POV | branch_condition | sequence_evidence | detail_link |

## 불명확한 순서·분기·병렬성
| source_path | 문제 | 알려진 정보 | 검증할 link/condition/실행 결과 |

## 매핑 갱신 원칙
- 파일명 정렬 순서를 플레이 순서로 단정하지 않음
- 소스 구조 변경 시 arc 인덱스와 링크 동시 갱신
```

**실제 필드가 없는 경우:** 단위 범위가 확인되지 않으면 `UNKNOWN`으로 둔다. 이름만으로 `branch_condition`이나 완료 엔딩을 지어내지 않는다.

## 8. `story/TIMELINE_AND_REVEALS.md` — 시간선·비밀·정보 공개 제어

서사에 소문, 회상, 시간 이동, 스포일러 위험이 있는 경우에 생성한다. 단순 연대기만 만들지 말고 **각 지식의 공개 경계**를 관리한다.

```md
# Timeline and Information Disclosure Registry

## 1. 직접 확인된 시점 단서
| clue_id | 원문 위치 | 직접 진술된 시점/순서 | 관찰자 | 확신도 |

## 2. 시간 순서 가설 (검증 여부 표시)
| event_a | relation_before_after | event_b | 출처 | 확정/추정 |

## 3. 번역에서 앞당겨서는 안 되는 정보
| info_id | 숨겨진 내용 | 처음 알게 되는 화자/독자 | 공개 scene/unit | 이전 시점에서 금지 표현 |

## 4. 세계관·인물 동일성·신분 변화의 충돌
| issue_id | 서로 충돌하는 진술 | 루트/시점 구분 | 판단 보류 이유 |

## 5. 필수 확인 질문과 우선순위
| 질문 | 필요한 원본 | 담당자 | 심각도 |

## 6. 관련 스토리·캐릭터·용어 문서
- 실제 상세 앵커 링크
```

## 9. `knowledge/DOMAIN_BIBLE.md` 및 `knowledge/topics/<topic-id>.md`

### 생성 조건과 분리

게임의 세계관/능력 체계, 앱의 기능 모델, 제조·법률·기술 매뉴얼의 개념처럼 **고유 용어의 명칭 이상으로 정의·관계·상태가 번역에 영향을 줄 때** 만든다. 명칭 표기는 Glossary, 기능/사실 정의는 Domain Bible, 실제 문장 적용은 해당 원문 단위가 기준이다.

```md
# Domain Bible — 개념 탐색 인덱스

## 1. 도메인 범위와 참조할 1차 자료
## 2. 개념/기능/세계관 요소 색인
| concept_id | 원문 명칭 | 개념 구분 | 상세 링크 | 버전/출처 |
## 3. 관계/위계/상태 전이 개요
## 4. 스코프별 유효성(제품 버전/지역/루트)
## 5. 미확정 또는 상충 정의
```

```md
# [도메인 주제] — TOPIC-001

## A. 원문에 확인된 정의/목적
## B. 관련 개념과 상하위·포함 관계
## C. 기능/상태/조건/예외
## D. 사용자/인물 관점에서 달라지는 의미
## E. 번역에 미치는 영향과 피해야 할 오역
## F. 용어집 매핑과 실제 단위 예
## G. 버전별 차이, 원문 ID, 승인 상태
```

**예:** 사용자 인터페이스에서 `archive`가 '보관함으로 이동'인지 '영구 보존 처리'인지는 기능 근거로 확인한다. 제품 기능이 확정되지 않았는데 번역어를 먼저 고정하지 않는다. 특수한 세계관의 '기억'이라는 단어를 보통 명사로 획일 치환하지 않는다.

## 10. `media/UI_CONTEXT.md` — UI 위치·상태·문맥

UI 중심 프로젝트에서 실제 원문 문자열과 화면 연결이 확인될 때 만든다. UI 자산은 인물/스토리와 무관하게 독립될 수 있다.

```md
# UI Translation Context

## A. 제품/플랫폼/로캘과 접근 가능한 테스트 환경
## B. 화면·컴포넌트·문구 매핑
| string_id | 화면/기능 | 사용자 상태 | 현재 행동 | UI 타입 | 원문 | 허용 길이 | 링크/스크린샷 근거 |
## C. 작업·결과·오류 메시지의 톤 기준
## D. 버튼 vs 상태 vs 명령문 구분
## E. 자리표시자/태그/인라인 마크업 보호
## F. 접근성·레이블·도움말·복수형/성별 처리
## G. 기기/해상도별 실제 검증과 미해결 문제
```

**문맥의 의미:** 같은 단어 `Save`도 버튼의 '저장', 저장 상태의 '저장됨', 파일 보관의 '보관'일 수 있다. 의미 판단에 화면 상태와 사용자 행동을 넣는다. '최대 글자 수'가 확인되지 않으면 숫자를 만들어 넣지 않는다.

## 11. `media/SUBTITLE_CONSTRAINTS.md` — 자막·타이밍·분할

영상·방송·교육 동영상 등에서 타임코드/발화자의 전환이 실제 번역에 영향을 줄 때 만든다.

```md
# Subtitle and Caption Constraints

## A. 기준 영상/스크립트/타임코드 자료와 버전
## B. 단위 식별과 컷/화자 전환
| cue_id | start | end | speaker | source_text | scene | overlaps | source_ref |
## C. 목표 로캘별 자막 스타일·호흡 기준
## D. 줄 수/자수/읽기 속도 제한 (프로젝트/플랫폼 확정 수치만)
## E. 중복 발화/화면 텍스트/청각 정보 처리
## F. 번역상 압축 허용 범위와 의미 누락 위험
## G. QA: 타이밍·줄바꿈·가독성·중첩 검증
```

자막 속도를 근거 없는 고정값으로 선언하지 않는다. 원본 자막 파일의 타임코드를 번역 편집의 편의를 위해 변경하지 않는다. 실제 영상 확인 전에 립싱크/가독성 검증이 끝났다고 하지 않는다.

## 12. 생성 조합과 완료 조건

| 프로젝트의 실제 성격 | 기본 문서 + 조건부 계층 | 중요한 번역 지식 |
|---|---|---|
| 대사/캐릭터 중심 게임 | `02`, `characters/`, 필요 시 `story/`와 `06` | 화자→상대·시점별 호칭, 원문 단위, 분기·정보 공개 |
| 비주얼 노벨/소설 | `02`, `03`, `characters/`, `story/` | 서술자, 관계, 장면·시점, 소문/반전, 용어 |
| 앱·웹 UI | `06`, `media/UI_CONTEXT.md`, 필요 시 `knowledge/` | 화면 상태·문구 종류·변수 보호·길이 |
| 영상 자막 | `06`, `media/SUBTITLE_CONSTRAINTS.md`, 화자가 중요하면 `02` | 발화자·시점, 타임코드, 줄분할·압축 |
| 기술·학술·매뉴얼 | `knowledge/`와 심화 `glossary/`, `06`(포맷이 있으면) | 개념 정의, 절차·조건·버전·단위, 표기 |
| 혼합 프로젝트 | **실제 쓰이는 계층을 조합** | 공통 정책을 한 번 쓰고 분야 인덱스로 분기 |

**완료 조건:** 인덱스에서 실제 있는 상세 파일로 이동되고, 상세 파일에는 번역 영향과 적용 조건이 있으며, 모든 확정 주장은 원문·결정 근거로 돌아갈 수 있어야 한다. 단순히 파일이 있다는 것은 완료가 아니다.
