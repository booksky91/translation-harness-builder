# 완성 기준, 내용 검증, 자체 구축 수락 테스트

이 문서의 핵심은 **파일 목록이 맞는 것**이 아니라 **그 문서를 읽으면 번역 업무를 진행할 수 있는가**다. 자료가 없을 때는 사실이 채워지지 않을 수 있지만, 양식의 문서 책임·작성 기준·조회·승인 절차는 완전해야 한다.

## 목차
1. 단계를 분리한 성공 판정
2. 단일 하네스의 공통 구조·내용 수락 기준
3. 각 문서의 내용 깊이 검사
4. 조건부 계층 테스트
5. 증거·승인·실행 검증 테스트
6. 생성·갱신 무손실 검사
7. Rule 및 무손실 갱신 테스트
8. 완료 보고 양식

## 1. 별개의 네 품질 관문

| 게이트 | 무엇을 확인하는가 | 완료 증거 | 혼동 금지 |
|---|---|---|---|
| `G0_STRUCTURE` | 폴더/문서/섹션/링크/Rule 구조 | 실제 파일 열람, 링크 점검 | 파일 수만 맞추는 것 아님 |
| `G1_EVIDENCE` | 사실과 적용 조건이 원문 위치·버전에 연결됨 | 실제 원문 대조 기록 | 단순 파일명·추측 아님 |
| `G2_LANGUAGE` | 의미·대사·용어·서사·문체 판단 검수 | 검토자/승인 기록 | 초안과 승인 혼동 금지 |
| `G3_RUNTIME` | 실제 매체 표시·태그·선택지·자막·기능 시험 | 실행 환경/빌드/결과 | 텍스트 승인만으로 통과 금지 |

구조가 생성됐지만 소스가 없으면 `G0 통과 / G1~G3 미실시`가 정상적인 보고일 수 있다. 사용자가 원하는 수준을 부풀리지 않는다.

## 2. 구조·내용 수락 기준

각 문서의 실제 내용과 연결 상태를 다음 기준으로 확인한다.

- [ ] 프로젝트에 **단일 활성 번역 하네스 루트**가 지정되고 실제 문서를 열 수 있는가? 기존 경로를 무단 이동하거나 병렬 구조를 추가하지 않았는가?
- [ ] `translation-harness/`(또는 지정한 경로)의 필수 문서들이 존재하고 필요한 내용 항목이 작성되었는가?
- [ ] README가 목적, 범위, 진입점, 문서별 책임, 출처/승인 링크, 미확정 상태를 **실제로 설명**하는가?
- [ ] 중앙 가이드가 작업별 로드 표·판단 우선순위·보류 조건을 갖추고 **정확히 존재하는 상세 절**로 이어지는가?
- [ ] 단위 작업 계약에 원본 ID, 문맥, 입력·출력·보존 필드, 미확정 처리 방법이 있는가?
- [ ] 필수 `guides/01_EXECUTION`, `04_TARGET_STYLE`, `05_TERMS_AND_NAMES`, `07_QA_APPROVAL`에 실질적 판단 규칙과 표·체크리스트가 있는가?
- [ ] 용어집에 원어/개념/목표어/상태/적용/예외/근거/승인 필드가 있으며, 용어가 0건이어도 등록법을 설명하는가?
- [ ] `operations/SOURCES`, `DECISIONS`, `ISSUES`, `QA_LOG`, `CHANGELOG`가 존재하며 의미·필수 항목·갱신 절차를 설명하는가?
- [ ] 대사/스토리/UI/자막 등 조건부 계층은 **필요한 것만** 추가하거나 보강했고 확인되지 않은 상세 데이터를 생성하지 않았는가?
- [ ] 인덱스→상세 문서→상위 인덱스 링크가 유효하고 관련 근거·승인 기록은 안정된 ID로 연결되는가?
- [ ] 문서 안에 빈 제목/TODO만 남겨 필수 판정 규칙이 실질적으로 누락되는 일이 없는가? 실제 사실이 없는 셀은 `UNKNOWN` 또는 미조사 상태로 구분했는가?
- [ ] 프로젝트 Rule이 번역 전에 **실제 진입 문서와 해당 상세 본문**을 읽도록 지시하는가?
- [ ] 문서 설계 명세를 이용하여 필요한 폴더·파일·섹션을 실제로 생성·보완했는가?

## 3. **각 문서에 필요한 정보** 검증

| 문서 | 질문과 합격 기준 |
|---|---|
| README | 무엇을 하며 어디로 이동해야 하고 무엇이 미확정인지 바로 알 수 있는가? |
| TRANSLATION_GUIDE | 지금 대사/자막/UI/용어 작업이면 **어떤 상세 파일과 절을 열어야 하는지** 알 수 있는가? |
| PROMPT_TEMPLATE | 실제 번역 단위의 ID, 문맥, 원문, 보호 요소, 출력·기록 상태가 정의되는가? |
| EXECUTION | 원본 확인부터 상세 로드·번역·QA·기록까지 순서와 충돌 우선순위가 있는가? |
| DIALOGUE_VOICE | 화자·상대·시점·목적에 따른 말투 결정 원칙을 안내하고 실제 인물 규칙과 분리하는가? |
| NARRATION_STORY | 소문·추론·서술 진실·스포일러와 분기 시점을 구별하는가? |
| TARGET_STYLE | 로캘 확인 여부, 문장 유형, 표기/길이/예외/근거가 분리되는가? |
| TERMS_AND_NAMES | 애칭·독음·동형이의어·스포일러 표기/승인 조건을 설명하는가? |
| FORMAT_AND_TECH | 실제 포맷에 따라 불변 필드/변수/태그/분기/검증 범위가 구분되는가? |
| QA_APPROVAL | 오류 심각도, 리뷰 상태 전이, 승인 책임, 텍스트/실행 검증 분리가 있는가? |
| CASEBOOK | 실제 원문 ID, 맥락, 후보, 선택 이유, 반례, 상태가 있는가? 가상 성공 사례를 만들지 않는가? |
| GLOSSARY | '원어→목표어'만이 아니라 개념 ID, 변형, 적용 조건, 상태, 출처가 있는가? |
| CHARACTER_BIBLE | 인덱스가 상세 화자/수신자 **방향** 링크를 제공하는가? |
| 인물 카드 | 실제 상대별 말투 절에 관찰/대안/시점/예외/근거/승인 정보가 있는가? |
| STORY_BIBLE | 파일/루트/장면이 상세 매핑되고 공개 정보 상태를 탐색할 수 있는가? |
| 스토리 카드 | 단순 줄거리 대신 장면별 인물 지식·정보 공개와 번역 영향이 기록되는가? |
| TIMELINE | 확인된 시점 단서와 순서 추측을 구분하고 스포일러 역유입을 막는가? |
| DOMAIN/UI/SUBTITLE | 실제 기능·화면·타임코드·매체 제약과 원문 근거가 함께 있는가? |
| SOURCES/DECISIONS/ISSUES/QA_LOG/CHANGELOG | 근거 위치, 승인, 미해결, 실기기 시험, 변경 영향을 서로 혼합하지 않는가? |

## 4. 조건부 계층 검증 시나리오

### 이야기 중심 번역

- 존재하는 인물만 `profiles/`에 기록하고 새 인물마다 실제 원문 ID가 있는가?
- 인물 A→B와 B→A의 호칭을 구분하는가?
- 시점에 따라 신분/관계/알고 있는 사실이 달라지는 경우 루트 및 인물 상세에 따로 기록되는가?
- `CHARACTER_BIBLE`, `STORY_BIBLE`이 상세 파일을 복제하지 않고 **해당 앵커로 이동**시키는가?

### 제품 UI 번역

- 캐릭터/스토리/가짜 루트 파일이 생기지 않았는가?
- 버튼/상태/에러, 변수, 길이 제한, 실제 화면 문맥을 `media/UI_CONTEXT`와 기술 가이드에 기록하는가?
- 화면/상태가 확인되지 않은 문자열을 하나의 표면형만 보고 전역 치환하지 않는가?

### 자막 번역

- 자막 cue ID와 타이밍·발화자·화면 상태를 관리하는가?
- 자료에서 확인되지 않은 초당 문자 수/글자 수 제한을 가상의 회사 정책으로 단정하지 않는가?
- 문맥상 화자가 중요하다면 대사 가이드와 연결하는가?

### 소스 없는 새 프로젝트

- 기본 문서가 **실제 정책과 작성 규격으로 완성**되어 있는가?
- 캐릭터·루트 숫자, 작품 설정, 용어, 승인/실행 검증을 지어내지 않았는가?
- 아직 확인할 자료와 필요한 정보가 SOURCES/ISSUES에 분명히 기록되어 있는가?

## 5. 근거/승인/실행 상태 검증

- [ ] 확정 주장마다 실제 `source_id`와 단위/위치/버전이 있는가?
- [ ] 관찰한 발화 사실과 객관적 세계관 사실을 혼동하지 않는가?
- [ ] 추정/후보/승인/실제 구현 검증 상태를 각기 별도 축으로 관리하는가?
- [ ] `APPROVED_TEXT`라면 실제 승인자와 적용 범위·결정 ID가 있는가?
- [ ] `RUNTIME_VERIFIED`라면 실제 기기/빌드/영상·화면 등 시험 환경과 결과가 있는가?
- [ ] 바뀐 정책에 영향을 받는 기존 번역 ID를 추적하고 회귀 검수할 수 있는가?

## 6. 생성·갱신 무손실 검사

구조 누락, 기존 기록 보존, 반복 실행의 안전성을 점검한다.

- [ ] **빈 프로젝트:** 하네스가 없어도 필수 폴더·Markdown 문서·작성 규칙을 스스로 생성했고, 원문 사실은 꾸며내지 않았는가?
- [ ] **기존 문서:** 폴더와 문서·목차·표를 중복 생성하지 않고 누락된 근거와 판정 정보를 채웠는가?
- [ ] **부분 골격:** 일부 필수 파일·섹션이 빠져 있어도 같은 위치에 누락분만 보완하고 상위 링크를 갱신했는가?
- [ ] **일부 실내용 작성됨:** 기존 정책, 용어 항목, 승인자 기록, 이슈·원문 출처가 사용자 동의 없이 초기화되지 않았는가?
- [ ] **외부 문서 도입:** 기존 내용을 보호하면서 필요한 문서를 편입하고 상대 경로·Rule은 실제 파일을 가리키는가?
- [ ] **다시 실행:** 같은 입력 조건에서 기존 내용을 중복 삽입하거나 폴더를 중복 복제하지 않는가?

## 7. Rule/갱신 안전성 테스트

- [ ] 기존 `AGENTS.md`나 에이전트 Rule의 다른 내용을 보존하는가?
- [ ] Rule은 **번역 전** 최상위 문서와 필요한 상세 본문을 읽도록 지시하는가?
- [ ] Rule의 경로와 중앙 가이드의 상대 링크는 실제 존재하는가?
- [ ] Rule을 두 번 갱신해도 같은 관리 블록/지시가 중복되지 않는가?
- [ ] 새 인물/용어/루트를 추가하고 나서 인덱스·상세 링크·CHANGELOG·QA 영향 목록이 갱신되는가?
- [ ] 시스템이나 에디터가 실제로 규칙을 로드하는지 테스트하지 않았으면 '로딩 미검증'이라고 보고하는가?

## 8. 완료 보고 양식

다음 정보를 짧고 명확하게 보고한다.

```text
기존 폴더 현황 및 보완 내용: [기존 문서 / 새로 생성한 문서 / 추가한 필수 섹션]
활성 하네스 루트: [실제 프로젝트 경로; 공통으로 사용]
진입점 / 라우터: [실제 문서 경로]
구축·보완한 문서: [진입점, 공통 정책, 분야 인덱스, 상세, 운영 기록]
프로젝트 사실을 실제 원문으로 채운 범위: [원본 식별자와 열람 범위]
지식 상태: [확인됨 / 미확정 / 충돌 / 미승인]
Rule 반영: [실제 파일, 기존 내용 보존, 읽기 대상 경로]
G0 구조·라우팅: [통과/미완료 + 이유]
G1 원문 근거: [통과/부분/미실시]
G2 언어·승인: [통과/부분/미실시]
G3 실행 매체: [통과/미실시]
후속 작업: [필요한 원본/검토/테스트]
```

최종 수락 기준은 **문서별 정보 책임·작성 규격·실제 문서 링크·근거 상태·Rule 연결**이 프로젝트에서 활용 가능한 수준으로 구현되었는지다.
