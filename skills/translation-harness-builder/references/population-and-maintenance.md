# 생성·내용 작성·관계 연결·장기 갱신 플레이북

프로젝트 파일을 조사하고, 하네스 문서를 구성한 다음 근거 기반 내용을 작성·갱신하는 작업 순서다.

## 목차
1. 프로젝트·현재 폴더·문서 인벤토리
2. 누락된 문서 골격 생성·보강
3. 문서별 필수 정보·링크·보존 확인
4. 원문 지식 조사 방법
5. 문서별 내용 채우기
6. 상호 참조와 지식 중복 방지
7. 문서 분할/합치기와 범위 확장
8. 갱신 이벤트와 영향 분석
9. 예외/자료 부족/충돌 처리

## 1. 현재 프로젝트와 하네스 조사

1. 프로젝트 루트의 기존 README, 번역 정책, Rule, 원문 자료를 확인한다. 프로젝트가 명시한 소스 위치를 우선한다.
2. **작업 대상별 활성 하네스 루트**를 정한다. 단일 대상의 기본은 `PROJECT_ROOT/translation-harness/`이고, 여러 대상이 있다면 [workspace-scoping.md](workspace-scoping.md)에 따라 각각의 루트와 소스 소유권을 정한다. 운영 중이거나 사용자 지정 경로가 있다면 그 경로를 유지한다.
3. 현재 루트 아래의 폴더/Markdown 문서·제목·표·미작성 필드·상대 링크·승인 기록을 **실제 본문을 열어** 확인한다. 프로젝트 밖에서 폴더 템플릿이 제공됐다면 그 파일을 활성 루트에 비파괴적으로 반영한다. 다른 하네스를 하나 더 만들지 않는다.
4. [architecture.md](architecture.md), [authoring-blueprints.md](authoring-blueprints.md), [domain-knowledge-blueprints.md](domain-knowledge-blueprints.md), [evidence-and-governance.md](evidence-and-governance.md)의 필수 정보와 현재 문서 내용을 비교하고 누락된 구획을 보완한다.
5. 원문 자료를 아직 확보하지 못했다면 문서 구조와 정보 기록 양식부터 완성하고 조사 대상을 명시한다.

### 조사 중 기록할 실무 정보

| 질문 | 기록 위치 | 확인 불가 시 |
|---|---|---|
| 번역 목표와 언어쌍/로캘은? | README, style | UNKNOWN/잠정 정책 |
| 어떤 매체/표현 단위인가? | README, execution, sources | 출처 접근 필요 표시 |
| 원문 고유 ID는 무엇인가? | SOURCES, prompt | 추후 확인; 변경 금지 규칙은 유지 |
| 인물/화자/관계가 중요한가? | BIBLE 생성 여부 결정 | 추정 인물 생성 금지 |
| 사건/루트/시점 정보가 중요한가? | STORY 생성 여부 결정 | 실제 장면군 등장 후 생성 |
| 태그/선택지/UI/자막 제한이 있는가? | 기술/매체 가이드 선택 | 보편적 원문 보호만 유지 |
| 기존 승인자나 용어집이 있는가? | DECISIONS, GLOSSARY | 미승인 기본 상태 |
| 실제 사용하는 에이전트 Rule은? | 프로젝트 Rule | 없다면 AGENTS.md 기본 |

## 2. 폴더·문서·목차 구성

**파일 목록만 계산하거나 계획서만 남기지 말고 프로젝트 안에 실제 Markdown을 작성한다.** 모든 대상 문서에서 `현재 파일 열기 → 필수 내용 대조 → 없는 폴더/파일/섹션 만들기 → 사용자 작성 내용 보존 → 상세 링크 연결`을 반복한다.

1. 활성 루트의 `README.md`, `TRANSLATION_GUIDE.md`, `PROMPT_TEMPLATE.md`가 존재하는지 확인한다. 없는 파일만 새로 만든다. 있는 파일은 **본문을 재사용하면서** 작성 청사진에 필수인 목적·작업별 문서 라우팅·우선순위·입출력 계약 등을 빠진 만큼 보완한다.
2. `guides/`에 실행, 목표 문체, 용어 판단, QA 승인 정책을 보장한다. 이미 있는 가이드의 정해진 섹션과 표를 확인하여 채우고, 없는 경우 상세 목차까지 포함한 문서로 생성한다. 언어·로캘이 미확정이면 무엇을 확인해야 하는지와 보류 규칙을 적는다.
3. `glossary/GLOSSARY.md`에 등록 기준, 표제어와 대상 개념, 원어 표면형/변형, 번역 후보·적용 조건·예외·출처·승인 상태를 기록할 **실제 표와 항목 규격**을 보장한다. 원문을 보지 못했다면 항목은 꾸며내지 않는다.
4. `operations/SOURCES.md`, `DECISIONS.md`, `ISSUES.md`, `QA_LOG.md`, `CHANGELOG.md`를 확인하고 없으면 만든다. 있는 파일은 본문 계약을 점검한다. 기록이 0건이어도 **무엇을 어떤 상태와 ID로 기록할지**가 적혀 있어야 한다.
5. 프로젝트에 화자·서사·UI·자막·전문 지식이 존재하거나 번역 판단에 필요하면 `characters/`, `story/`, `knowledge/`, `media/`와 해당 정책 가이드 중 **필요한 상세 문서만** 추가 또는 보완한다. 확인되지 않은 가상 인물/루트 수를 채우지 않는다.
6. 인덱스가 지시하는 상세 파일을 실제로 생성/확인하고, 상세에는 메타정보·적용/금지 조건·증거 필드·역참조 링크를 갖춘다. 관련 정보는 `UNKNOWN`과 조사 대기 항목으로 처리할 수 있지만 **필수 필드 자체를 제거하지 않는다.**
7. `TRANSLATION_GUIDE.md`와 상위 인덱스에는 **실제로 존재하는 경로·앵커와 조회 조건**만 연결한다. 조건부 문서가 아직 필요하지 않다면 없는 경로를 완성된 링크처럼 만들지 않는다.
8. [rule-integration.md](rule-integration.md)를 적용하고 Rule의 진입 문서와 상세 조회 경로가 실제 열리는지 검사한다.

### 잘못된 결과의 예

- 기존 문서에 제목과 빈 표가 있다는 이유로 목차·용어 판단·근거·승인 필드의 누락을 그대로 둠.
- 빈 프로젝트에서는 README 하나만 만들고 나머지는 '템플릿이 없어서 불가능'하다고 보고함.
- `characters/profiles/`에 근거 없는 가상 인물을 여러 개 추가함.
- 중앙 가이드에 존재하지 않는 상세 문서 링크를 완료된 것처럼 삽입함.
- 용어집에서 `원어 | 번역어` 이외의 적용 범위·승인·근거 규칙을 생략함.
- 기존 프로젝트 정책·사용자 수정분을 새 Markdown 템플릿으로 덮어씀.
- Rule은 만들지 않고 README에 '읽을 것'만 적어 실제 번역 에이전트 연결을 누락함.

## 3. 내용 계약과 기존 기록 보존

1. 문서마다 필수 섹션, 표 컬럼, 적용 조건, 링크, 현재 상태를 검사하고 빠진 항목을 안전하게 추가한다.
2. 기존에 작성된 사실·번역안·정책·승인 기록은 그대로 보존한다. 승인된 문구를 바꿔야 한다면 기존 결정을 추적하고 승인 범위를 다시 확인한다.
3. 제목이나 컬럼명이 청사진과 달라도 **동일한 의미·역할이면** 중복 섹션을 추가하지 않고 사용한다. 다른 의미이거나 충돌하면 `ISSUES.md`에 기록하고 무단으로 지우지 않는다.
4. 문서 안의 예시값·가상 문장·플레이스홀더는 프로젝트 사실이나 승인 번역으로 간주하지 않는다. 실제 원문과 연결된 항목만 검증된 지식으로 취급한다.
5. 정보 기록 양식만 존재하는 문서는 완료로 표시하지 않는다. 실제 근거 수집, 내용 작성, 검수, Rule 연결, 구조 검증의 결과를 각각 확인한다.

## 4. 원문을 읽고 번역 자산을 채우는 조사 프로토콜

### A. 자료 소스와 단위 식별

- 원문이 문서라면 절/문장/페이지, 문자열 테이블이라면 키/행 ID, 스크립트라면 장면/대사 ID, 영상이라면 타임코드/cue ID를 확보한다.
- 기존 원본의 ID가 없다면 안정된 임시 식별자를 작성하고 그 출처/구성법을 SOURCES에 기록한다.
- 분석할 수 있었던 파일, 전체 중 어느 범위를 **원문 본문까지 실제 읽고 문맥을 비교했는지**, 미독 파일/다른 버전이 있는지를 분명히 기록한다. 목록 추출은 본문 읽기 완료로 취급하지 않는다.

### B. 판정 가능한 최소 문맥으로 확장

- 인물 대사: 해당 문장만이 아니라 **수신자를 입증하는 직접 호칭·상호 발화·장면 참여와 공적/사적 상태**를 찾는다. 단순 직전 발화에 의존하지 않는다.
- 스토리: 특정 등장인물의 현재 지식, 루트/장면 조건, 시간 변화, 소문/추측 여부를 확인한다. 파일명 정렬로 순서를 확정하지 않는다.
- 용어: 실제 지칭 대상, 원문 형태/변형/독음, 장면별 별칭·표기 의도를 확인한다.
- UI: 문구의 버튼/결과/상태/오류 역할, 화면 위치, 사용자 행동, 변수를 확인한다.
- 자막: 화면·발화자·시간코드·겹침·청각 정보·줄 분할을 확인한다.
- 전문 문서: 용어 정의, 전제 조건, 경고/금지/부정, 제품/기술 버전과 관련 단계를 확인한다.

### C. 관찰에서 판단까지 분리

항목마다 `source/unit ID → 실제 관찰 → 필요한 문맥 확인 → 해석(있다면) → 목표어 후보 → 해당되는 조건 → 안 되는 반례 → 승인/시험 상태`로 작성한다. 근거를 찾을 수 없으면 `UNKNOWN/INFERRED`를 쓰고, 소문 내용을 객관적 사실로 바꾸지 않는다.

## 5. 자산별 내용 입력 우선순위

- **SOURCES:** 사실 주장보다 먼저 출처 ID·버전·범위를 정리한다.
- **GLOSSARY:** 고유명사·동음이의어·전문어를 원문에 있는 형태 그대로 등록한 뒤 변형·지칭 대상·상태·사용 조건을 연결한다.
- **CHARACTER_BIBLE/profiles:** 실제 발화 화자를 확인하고, 인물 상세에서 기본 화법을 분리한 뒤 **화자→수신자→관계 단계**별 규칙을 등록한다. 두 인물이 친하다는 설명만으로 상대별 종결어미를 확정하지 않는다.
- **STORY_BIBLE/arcs:** 원본 파일을 장면군과 매핑하고, 인물의 지식 상태·서술자·루트별 사건·정보공개 조건을 입력한다. 결말 정보가 이전 시점에 새어 나가지 않게 한다.
- **DOMAIN_BIBLE/media:** UI/제품/기술 용어의 기능·화면 상태·제약·예외를 실제 자료에서 확인한다.
- **DECISIONS/ISSUES/QA_LOG:** 번역자가 제안했는지, 맥락 검토가 끝났는지, 승인자가 있는지, 실제 매체 시험까지 했는지를 서로 다른 필드에 기록한다.
- **중앙 라우터와 인덱스:** 실제 신규 문서나 적용 조건이 생기면 링크와 조회 조건을 갱신한다. 문서 내용 전체를 중앙 가이드에 복사하지 않는다.

## 6. 이중 저장을 막는 상호 참조 관리

### 단일 기준과 참조 방향

- 기준 용어 표기 = GLOSSARY. 캐릭터 카드에 표기를 다시 확정하지 말고 `T...` 용어 ID를 연결한다.
- 특정 인물의 상대별 화법 = 그 인물 프로필의 앵커. 인덱스에는 탐색 링크만 둔다.
- 현재 장면에서 누가 어떤 사실을 알고 있는가 = 해당 arc 문서 또는 타임라인. 대사 규칙은 그 지식 경계를 참조한다.
- 승인 이유 = DECISIONS. 실제 규칙 문서에는 상태와 decision_id만 노출한다.
- 실제 원문 위치 = SOURCES. 상세 문서에는 그 위치로 돌아가는 source_id/unit_id를 둔다.

### 역참조와 업데이트 확인

- 새 인물 카드 → 캐릭터 바이블에 새 인물/상대 링크 → 중앙 라우터의 적용 조건 점검.
- 새 루트 상세 → STORY_BIBLE과 FILE_INDEX/타임라인 링크 갱신 → 관련 인물 화법과 용어 스코프 검토.
- 새 승인 용어 → glossary 확정 상태 수정 → 기존 번역·캐릭터·스토리의 영향 단위 검색 → 변경·QA 기록.
- 규칙이 이동하거나 제목이 바뀌면 기존 앵커/상대 링크를 유지하거나 모든 참조 위치를 명시적으로 수정한다.

## 7. 언제 상세 문서를 쪼개거나 합칠 것인가

**분할 기준은 파일 개수나 글자 수가 아니라 조회 조건이다.** 같은 작업에서 늘 함께 열어야 하는 내용은 함께 두고, 다른 루트/역할/버전이라서 조건부로만 열어야 하는 내용은 분리한다.

- 화자 한 명의 상대별 규칙이 많다면 프로필 하나에 대상별 안정된 앵커를 사용한다. 특정 관계가 매우 복잡하고 독립적으로 갱신된다면 하위 파일로 분리하되 인덱스와 링크를 유지한다.
- 스토리 루트가 없는데 '루트1~루트12' 같은 폴더를 만들지 않는다. 실제 사건군 또는 챕터가 분리 조회 대상인지 보고 나눈다.
- UI가 수십 화면이고 기능별 정책이 다른 경우 `media/screens/<screen-id>.md`처럼 조건부 계층을 확장한다. UI_CONTEXT에는 탐색 인덱스를 둔다.
- 용어집은 기본 하나의 기준 파일로 유지하되 엄청난 규모/정책별 접근 차이가 있으면 `glossary/topics/` 등으로 분할하고 기준 인덱스를 유지한다.
- 제품 버전·로캘별 차이는 분리 필요성이 실제로 확인된 뒤 `scope` 또는 버전별 파일로 관리한다.

## 8. 갱신 트리거와 영향 그래프

### 트리거

- 새로운 원본/스크립트/번역본이 추가되거나 기존 원본 버전이 바뀜.
- 새로운 인물·상대 관계·루트·장면·제품 기능·화면이 확인됨.
- 검수자가 특정 번역어·호칭·표현을 승인하거나 반려함.
- 기술 테스트가 실패하거나 새 플랫폼의 제한이 추가됨.
- 이전 추론이 직접 근거와 충돌함.

### 실제 갱신 순서

1. 새 원본과 이전 출처의 위치·버전·차이를 확인한다.
2. 변경된 `source_id/unit_id/term_id/character_id/arc_id`를 식별한다.
3. 영향받는 문서, 참조한 정책, 현재 번역 단위, 승인 결정을 찾는다.
4. 사실/제안/승인 상태를 재평가한다. 승인된 결정을 자동 덮어쓰지 않는다.
5. 기준 문서 **한 곳**을 변경하고 인덱스·역참조·Rule 경로를 수정한다.
6. 영향받은 단위를 다시 QA하며, 실제 매체 검증도 필요하면 시험한다.
7. `CHANGELOG`에 변경·영향·검증 여부를 기록한다.

**유실 방지:** 직접 수정한 정책/원문 근거/승인 기록은 아무 설명 없이 템플릿으로 재초기화하지 않는다. 불확정 상태로 이동하거나 폐기해야 할 경우 이전 내용을 추적할 수 있어야 한다.

## 9. 자료 부족/문서 누락/충돌 시 처리

- 원문이 없어도 **기본 하네스의 정책·운영 문서와 구체적 작성 규격**은 구성한다. 도메인 사실만 `UNKNOWN`으로 남긴다. 현재 골격이 있으면 그 파일 안에 보완하고, 없으면 직접 만든다.
- 원문은 있으나 장면 전후 문맥이 빠졌다면 인물 관계나 사건 진실을 확정하지 않는다. 제한된 범위의 번역 초안만 만들 수 있으면 그렇게 보고한다.
- 세부 문서를 열 수 없으면 열었다고 보고하지 않는다. 필요한 본문 확보 또는 해당 쟁점 보류가 우선이다.
- 출처끼리 모순되면 원문 자체 오류인지, 루트/시점 분리인지, 번역 결정 충돌인지 먼저 구별해 ISSUE를 만든다.
- 기존 문서가 청사진의 구조 요구와 다르면 **필수 누락은 안전하게 보완**하고, 내용 충돌·기존 승인 삭제 등 비파괴적으로 처리하기 어려운 변경은 `ISSUES`에 기록해 검토를 요청한다.
- 작업 완료 보고에는 `문서 골격 및 필수 내용 계약 충족`, `자료를 근거로 내용 작성`, `검수 승인`, `실제 실행 검증`의 도달 수준을 각각 기록한다.

## 10. 원문 코퍼스 전수 분석과 실제 지식 반영

원문이 주어졌다면 앞선 1~9절만으로 일을 끝내지 말고 다음을 수행한다.

1. [corpus-ingestion.md](corpus-ingestion.md)의 전체 범위 등록, 본문 직접 읽기, 화자/분기/상태 복원, 배치별 체크포인트를 따른다.
2. [semantic-population.md](semantic-population.md)에 따라 인물의 상대별 말투, 사건의 인과·시점·정보 공개, 용어의 지칭 개념·예외, 실제 UI/기술 제약을 **실제 Markdown의 상세 본문**으로 작성한다. 파일명·행 수·원문 문자열 목록만 남기지 않는다.
3. 발견한 대상·출현 맥락과 완성된 상세 문서를 역추적하여 빠진 관계/장면/의미를 다시 읽는다.
4. [coverage-and-resumption.md](coverage-and-resumption.md)의 `SOURCES`/`WORK_LEDGER`를 갱신하고, 미독·미반영 소스가 있는 경우 진행 중으로 보고한다.
5. 여러 프로젝트라면 각 대상의 소스·쓰기 경로·Rule·검증 상태를 독립 관리한다. 한 대상의 완료를 전체 대상으로 전용하지 않는다.

중요한 번역 사례에는 실제 적용할 후보 표현, 선택 이유, 적용·금지 조건, 짧은 원문 근거와 위치를 적는다. 사람의 승인·매체 실행 시험은 실제 이력이 있을 때만 표시한다.
