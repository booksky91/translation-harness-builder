# 복수 프로젝트의 소스·하네스·Rule 범위 분리

하나의 저장소·워크스페이스에 여러 작품, 게임, 제품, 로캘 또는 클라이언트 프로젝트가 있을 수 있다. 대상별 자료 소유권과 번역 지식의 효력 범위를 정한 뒤, 각각의 하네스에서 동일한 조사·집필·검증 절차를 수행한다.

## 목차
1. 대상 프로젝트 식별
2. 작업 범위와 하네스 경로 지정
3. 기존 문서·템플릿 편입
4. 교차 프로젝트 혼입 방지
5. 프로젝트 Rule의 라우팅
6. 범위 검증

## 1. 대상 프로젝트 식별

- 사용자가 지정한 프로젝트·제품·언어쌍·버전·로캘을 우선한다. 실제 폴더/설정에 확인 가능한 식별자를 대응한다.
- 이름이 비슷하더라도 원본 자료, 화자, 세계관, 용어, UI, 번역 결정이 별개라면 서로 다른 `scope_id`로 관리한다.
- 같은 소스 파일을 여러 대상이 참조하더라도 공유 자료인지, 각 프로젝트에서 다른 의미로 사용하는지는 별도로 확인한다.
- 대상 이름의 일치, 파일명 규칙, 외부 기억만으로 소속을 추론해 여러 프로젝트에 동일한 사실을 채워 넣지 않는다.

## 2. 작업 범위와 하네스 경로 지정

- 일반적인 한 프로젝트의 기본 경로: `PROJECT_ROOT/translation-harness/`.
- 동일 작업 공간에 여러 독립 대상이 존재하고 사용자 지시나 기존 구조에서 대상별 분리가 필요하면 다음처럼 구성할 수 있다. 식별자·경로는 실제 프로젝트 이름에 맞춰 결정한다.

```text
WORKSPACE_ROOT/
├── translation-harness/
│   ├── README.md                 # 선택: 대상별 진입점만 나열하는 작업공간 색인
│   ├── <scope-id-1>/
│   │   ├── README.md
│   │   ├── TRANSLATION_GUIDE.md
│   │   ├── guides/
│   │   ├── characters/ ...
│   │   └── operations/
│   └── <scope-id-2>/
│       ├── README.md
│       ├── TRANSLATION_GUIDE.md
│       ├── guides/
│       └── operations/
└── AGENTS.md                       # 실제 프로젝트의 Rule 방식에 따라 적용
```

- 사용자나 프로젝트가 이미 다른 위치를 운영 중이면 그 경로와 파일을 보존한다. 기본 트리를 강제로 이동·중복 생성하지 않는다.
- 각 `scope_id`에는 독립된 README, 중앙 라우터, 용어집, 상세 자산, SOURCES, DECISIONS, ISSUES, QA, 변경 기록을 둔다.
- 작업 공간 색인은 각 하네스로 이동하는 **링크와 소유 범위만** 관리한다. 모든 작품의 화법·용어·결정 규칙을 한곳에 섞지 않는다.

## 3. 기존 문서·템플릿 편입

- 사용 가능한 기존 폴더와 문서가 있으면 해당 대상의 하네스에 맞춰 실내용을 보존하고 필수 누락을 보완한다.
- 공통 템플릿이나 작성 지침을 각 대상에 복제할 수 있다. **다른 대상의 인물·서사·용어·승인 사실까지 승인된 내용으로 복제하지 않는다.**
- 이미 채워진 공통 문서를 여러 대상에 복제해야 한다는 명시적 요청이 있으면 원본을 보존하면서, 프로젝트 고유 기록의 적용 범위를 다시 확인할 때까지 `검증 대기`로 두고 각 대상의 소스와 대조한다.
- 기존 하네스 문서가 여러 프로젝트의 내용을 혼합했다면 항목별 소유권을 먼저 분류하고, 다른 프로젝트 문서를 임의 삭제·덮어쓰기하지 않는다.

## 4. 교차 프로젝트 혼입 방지

- 모든 원본 근거와 단위 ID에 `scope_id` 또는 소유 범위를 기록한다. 서로 다른 프로젝트가 같은 원본 키를 써도 ID 충돌이 생기지 않게 한다.
- 인물 이름이 같거나 번역 후보가 유사해도 근거 없이 상세 카드·승인·화법 규칙을 공유하지 않는다.
- 실제로 공통 적용되는 정책이 있다면 **그 정책의 근거·권한·적용 범위**를 명시한다. 공통 정책보다 프로젝트별 승인된 예외가 우선하는 조건도 기록한다.
- 파일 작업 전 `읽을 수 있는 소스 범위`와 `쓰기 허용된 하네스 경로`를 확정한다. 다른 대상의 하네스 문서를 조회할 필요가 있다면 읽기 목적·근거를 밝히고, 그 내용을 자동으로 현재 프로젝트의 사실로 복사하지 않는다.
- 한 대상만 작업하라는 요청에 다른 대상의 README, GUIDES, DECISIONS, QA 등 기록을 수정하지 않는다.

## 5. 프로젝트 Rule의 라우팅

실제 번역·교정·QA 작업 전에 입력 단위의 `scope_id`를 결정한 뒤 해당 대상의 README와 라우터를 읽도록 Rule을 만든다.

```text
입력 단위의 프로젝트/제품/로캘/경로 확인
→ 해당 대상의 정확한 하네스 루트 선택
→ 해당 README 및 TRANSLATION_GUIDE 본문 열람
→ 해당 대상의 정책·인물·스토리·용어·출처의 상세 절 열람
→ 원본과 실제 결정 상태 대조 후 번역/기록
```

- 소속이 모호하고 다른 하네스 규칙이 결과를 바꿀 수 있으면 임의로 선택하지 말고 해결 질문을 `ISSUES`에 기록한다.
- 상위 작업 공간의 Rule에 프로젝트별 루트 매핑을 작성하거나, 실제 사용 중인 에이전트가 지원하는 범위 지정 Rule을 적용한다. Rule이 기술적으로 자동 호출되는지는 별도 확인한다.
- 하네스 구축·갱신 작업은 해당 하네스 안의 문서가 아직 없다는 이유로 차단하지 않는다.

## 6. 범위 검증

- 각 하네스의 `SOURCES`에 다른 프로젝트의 전용 원본이 포함되지 않았는가?
- 용어·인물·스토리·관계·기술 제약의 근거가 대상 `scope_id`와 같은가?
- 한 하네스의 수정 후 다른 하네스에 불필요한 파일 변경이 발생하지 않았는가?
- 작업 공간 색인·Rule에서 선택한 하네스가 실제로 존재하며 올바른 대상의 본문을 가리키는가?
- 모든 대상의 조사·집필·검증 상태를 **대상별로** 보고했는가? 한 대상만 충분히 작성됐는데 전체 완료로 표시하지 않았는가?
