# 조사 범위·의미 반영·미완료 재개·완료 판정

대규모 작업에서는 **읽었다고 보고하는 범위**와 **번역 지식을 문서에 실제 반영한 범위**를 별도로 검증한다. 문서 수, 링크 수, 코드 행 수, 문자열 수만으로 실내용 하네스의 완성을 선언하지 않는다.

## 목차
1. 시작 시 조사 범위 확정
2. 진행 원장과 상태 전이
3. 원본 대비 문서 내용의 커버리지
4. 배치·재개 작업 규칙
5. 불확실성 및 작업 종료 기준
6. 자체 검증과 보고 양식

## 1. 시작 시 조사 범위 확정

하네스의 대상 범위를 먼저 정의한다. 대상에 해당하는 자료가 여러 경로에 있다면 하나의 분모로 합칠지, 출처 유형별로 분리할지 기록한다. 공통 라이브러리와 다중 프로젝트 자료는 [workspace-scoping.md](workspace-scoping.md)에 따라 소유 범위를 확정한다.

- **번역 대상:** 실제 번역할 원문 문자열·대사·UI·자막·문서 및 해당 자료의 유효한 버전.
- **맥락 자료:** 인물·사건·제품 기능·화면·발화·용어 판단에 필요한 코드/설정/이미지·기존 번역과 프로젝트 가이드.
- **소스 가용성:** 발견했지만 못 읽음, 읽을 수 있음, 부분 읽음, 제외 사유 있는 파일을 구별.
- **논리 범위:** 텍스트가 몇 파일에 들어 있는지만이 아니라 실제 장면·화자·관계·분기·기능 화면 등 의미 단위의 조사 대상.

현재 소스를 발견할 수 없다면 범위 탐색 결과와 탐색하지 못한 위치를 기록한다. 파일을 전혀 읽지 못한 상태에서는 콘텐츠 완성이라고 보고할 수 없다.

## 2. 진행 원장과 상태 전이

`operations/SOURCES.md`의 조사 목록을 사용하고 규모가 크면 하네스 내부에 별도 `operations/WORK_LEDGER.md`를 생성한다. 프로젝트마다 실제로 기록할 수 있는 열만 쓰되 **분모, 실제 읽기, 의미 추출, 문서 반영, 검증 상태**는 반드시 구분한다.

| 열 | 필수 내용 |
|---|---|
| `scope_id` | 자료의 소속 프로젝트·로캘 |
| `work_id / batch_id` | 재개 가능한 처리 단위 ID |
| `source_id / unit_range` | 실제 확인할 소스 경로 및 구간·ID 범위 |
| `source_version` | 분석 중인 파일 버전/지문 |
| `discovered` | 원본 인벤토리에 등록했는가 |
| `context_read` | 본문과 영향을 주는 문맥을 실제 읽은 범위 |
| `extracted` | 발견한 지식 후보와 관찰/추론 구분 |
| `integrated` | 실제 작성한 하네스 상세·가이드·인덱스 링크 |
| `verified` | 원문 대조·반례 검사 여부 및 결과 |
| `unresolved / next` | 접근 실패, 불충분 근거, 다음 작업 구간 |

상태는 증거가 생길 때만 올린다. `발견 → 본문 열람 → 문맥 읽기 → 의미 추출 → 문서 반영 → 재대조`는 서로 다른 행위다. 문서 파일을 생성했다는 이유로 소스의 `integrated`를 완료 처리하지 않는다.

작업 진행률은 **실제로 측정 가능한 분모·분자**를 적어 계산한다. 예: `본문 문맥을 읽은 소스: X/Y`, `실제 문서에 반영한 소스: A/B`, `검토한 장면: M/N`. 분모를 알 수 없거나 소스가 동적으로 생성되어 전체 범위를 계산하지 못하면 숫자 대신 `범위 미확정`과 조사할 조건을 기록한다. 같은 원본의 중복 추출본을 양쪽에 넣어 비율을 부풀리지 않는다.

## 3. 원본 대비 문서 내용의 커버리지

적어도 다음 세 축을 대조한다.

| 축 | 어떻게 검사하는가 | 허위 완료의 예 |
|---|---|---|
| **소스 커버리지** | 범위 내 모든 원본 파일·섹션/문맥 자료를 실제 열람했는지, 미처리 이유를 기록 | 400개 파일명 수집만 하고 100% 조사라고 보고 |
| **의미 커버리지** | 확인된 주요 인물·상대 관계·장면·분기·용어·기능과 실제 하네스 카드/절을 대응 | 모든 선택지 ID만 등록하고 서사 정보 공개 분석을 완료로 표시 |
| **실용 커버리지** | 실제 작업 단위에서 적절한 규칙·적용 조건·반례·근거에 도달 가능한지 확인 | 상세 문서에 빈 표만 있고 링크 정상만을 합격으로 표시 |

모든 줄을 지식 카드로 1:1 복제할 필요는 없다. 중요 반복 사례·예외를 근거로 **번역에 필요한 규칙**을 충분히 추상화하고, 나머지 소스는 반례/누락 검증으로 다룬다. 각 파일의 정보가 기존 규칙으로 모두 처리되는 경우 그 검토 사실을 원장에 남긴다.

### 의미 단위 대조표

원본에서 발견한 대상 종류를 반영하는 목록을 만든다. 예를 들어 대사 기반 프로젝트면 `발화 화자`, `실제 수신자 또는 수신자 미확정`, `방향성 있는 관계`, `사건군`, `정보 공개 조건`, `지칭 개념`; UI 중심이면 `화면/상태/버튼/오류`, `변수·플레이스홀더`, `기능별 용어`, `플랫폼 제약`이다.

- `원문에서 발견한 대상 ID → 적용할 하네스 문서·앵커 → 근거 → 검토 상태`를 역추적한다.
- 근거 있는 중요한 대상을 누락했다면 해당 범주의 의미 반영은 미완료다.
- **모든 출현을 상세 카드를 새로 만들어야 한다**고 해석하지 않는다. 소스에 새 번역 판단 정보가 없으면 기존 정책으로 연결하며 그 이유를 기록한다.
- 원문에 없는 항목을 완성도를 높이기 위해 꾸며내거나, 미독 파일을 존재하지 않는 것으로 취급하지 않는다.

## 4. 배치·재개 작업 규칙

하나의 호출/작업 시간에 모든 소스를 읽을 수 없을 때 다음 방식으로 반복한다.

1. `WORK_LEDGER`(또는 SOURCES)에서 **아직 반영/검증되지 않은 배치**를 선택한다. 기존 완료 표시는 근거와 버전을 확인한다.
2. 배치의 원본을 실제로 읽고, 필요한 앞뒤 장면/상태를 확장해 의미 지식을 추출한다.
3. 원본 정보와 연결된 실제 하네스 문서를 수정하고 인덱스·중앙 가이드·근거 원장의 링크를 반영한다.
4. 배치별 `source_id`, 처리한 유효 구간, 작성한 내용·대상 문서, 판단 상태, 남은 질문, 다음 시작 구간을 기록한다.
5. 새로운 사실이 기존 규칙을 변경했다면 영향받는 과거 배치를 재검토 대상으로 표시한다.
6. 다음 실행에서 **인벤토리부터 무조건 다시 만들지 말고** 최신 유효 체크포인트부터 이어서 작업한다. 단, 원본/지침 버전이 달라졌으면 영향 범위를 새로 정한다.

### 유용한 체크포인트 형식

```md
### [batch_id] — [소스 집합 또는 논리 장면 범위]
- 대상 프로젝트: [scope_id]
- 파일/버전: [실제 확인한 경로·지문]
- 실제 열람 완료: [source/unit 범위]
- 발견한 중요한 정보: [주장·대조/반례·근거 ID]
- 실제 반영한 문서: [상대 링크와 앵커]
- 미검토 원문: [구체적 파일·구간]
- 문맥 미확정: [조사했으나 입증되지 않은 질문]
- 재개 지점/순서: [다음 배치 ID 및 선행 자료]
- QA 상태: [실제 수행한 검사만]
```

배치 자료를 열람하고 검사한 흔적 없이 완료 체크만 채우는 것은 진행률 증거가 아니다.

## 5. 불확실성 및 작업 종료 기준

각 대상 프로젝트의 상태를 다음과 같이 구분한다.

- `SCAFFOLD_ONLY`: 구조와 작성 계약만 있음. 접근 가능한 원본을 읽지 않았거나 없음.
- `POPULATING`: 원본 조사·문서 실내용 작성 중. 미읽음/미반영 범위가 남음.
- `DRAFT_CONTENT_COMPLETE`: 정한 접근 가능 범위의 원본 문맥 분석과 핵심 지식 반영, 교차 참조·내용 QA가 끝났으며 **번역 판단 초안이 실무적으로 사용 가능**. 사람의 승인 또는 런타임 시험은 아직 별도일 수 있음.
- `REVIEWED`: 요청된 언어/맥락 검토·승인이 실제로 수행됨. 승인자·범위 증거 필요.
- `RUNTIME_VERIFIED`: 실제 구현 환경에서 시험한 결과가 기록됨. 문서/정적 QA만으로 표시하지 않음.
- `BLOCKED`: 권한·누락 소스·도구 제약으로 접근 가능 범위를 끝낼 수 없는 상태. 완료 상태 대신 별도 차단 이유로 병기.

`DRAFT_CONTENT_COMPLETE`에 필요한 최소 증거:

1. 작업 대상의 유효 원본 목록과 소속·버전·번역 단위를 등록했고, 접근 가능한 해당 범위를 실제로 읽었다.
2. 각 자료의 의미 정보가 문서에 반영됐거나 의미 변화가 없는 이유와 연결된 규칙을 기록했다.
3. 프로젝트에 등장한 주요 인물/화법·관계, 사건/정보 공개·분기, 용어/개념, UI/기술 제약 중 **실제로 해당되는 분야**가 상세 지식과 가이드에 반영됐다.
4. 원문에 확인된 대표 사례·다른 장면의 반례·예외, 적용 조건, 출처가 있어 실제 번역 단위에 적용할 수 있다.
5. 미확정 질문은 `UNKNOWN`으로 두되 `NOT_READ`와 구별했고, 범위 내 미처리 자료·검증 누락이 없다.
6. 하네스 인덱스와 Rule이 실제로 존재하는 문서·절을 참조하고, 표본 작업의 전체 조회 경로를 점검했다.

중요: 모든 번역 문장을 최종 승인·배포해야만 **초안 하네스의 내용 작성**이 끝나는 것은 아니다. 반대로 문서 골격, ID 수집, 일부 문자열 번역만 했으면 초안 하네스의 내용 작성이 완료되지 않은 것이다.

## 6. 자체 검증과 보고 양식

결과 보고에는 문서·링크 개수뿐 아니라 다음 범위를 실제 수치 또는 구체적 목록으로 제시한다.

```text
대상 범위: [scope_id/원본 경로/버전/포함·제외 사유]
소스 발견: [파일/논리 장면/문자열/기능의 확인 가능한 총 범위]
원문 실제 열람: [완료 범위 / 미독·접근 불가 범위]
의미 분석: [인물·관계·서사·용어·UI 등 발견한 주요 대상과 비교 여부]
실제 지식 작성: [각 분야의 채워진 문서·절·적용 가능한 내용 예]
진행 원장: [SOURCES 또는 WORK_LEDGER 실제 경로/다음 배치]
내용 QA: [원문 재대조·예외·누락·혼입 검사 결과]
프로젝트 Rule: [실제 경로/읽기 동작 검증 여부]
상태: [SCAFFOLD_ONLY / POPULATING / DRAFT_CONTENT_COMPLETE / REVIEWED / RUNTIME_VERIFIED] + [BLOCKED 사유]
미완료: [파일/단위/검토·승인·매체 시험의 남은 범위]
```

에이전트가 실제로 읽지 않은 자료나 작성하지 않은 내용을 보고하지 않는다. 작업을 전부 수행할 수 없는 경우에는 실제 완료한 범위까지 수행한 뒤 **명확한 미완료 목록과 재개 가능한 체크포인트**를 남긴다. 다음 실행이 필요한 경우 사용자에게 그 상태를 알려야 하며 비동기 완료를 약속하지 않는다.
