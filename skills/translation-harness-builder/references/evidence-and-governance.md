# 출처·확신도·결정·검수·변경 자산의 실제 구성

운영 기록은 **실제 근거로 확인한 사실**, **번역 표현에 대한 결정**, **실행환경 검증 결과**를 분리해 관리한다. `operations/`에 필요한 기록 문서를 만들고, 기존 기록과 승인 내역은 보존하면서 누락된 필드를 보완한다.

## 목차
1. 인식/번역/검증의 서로 다른 상태
2. 출처 기록 `operations/SOURCES.md`
3. 결정 기록 `operations/DECISIONS.md`
4. 미확정·충돌 기록 `operations/ISSUES.md`
5. 검수·매체 시험 기록 `operations/QA_LOG.md`
6. 변경 기록 `operations/CHANGELOG.md`
7. 번역 단위별 공통 기록 계약
8. 문서 간 소유권·증거 참조·승격 규칙

## 1. 세 가지 상태 축은 별개로 관리

### A. 근거의 상태 (이것이 사실인가?)

| 상태 | 정확한 정의 | 허용되는 사용 |
|---|---|---|
| `UNKNOWN` | 관찰할 원문/맥락을 찾지 못했거나 접근 불가 | 미확정으로만 표기 |
| `OBSERVED` | 특정 출처의 실제 원문에서 표면 정보가 관찰됨 | 그 범위의 언어 사실로 사용 |
| `CONTEXT_CONFIRMED` | 충분한 앞뒤 문맥, 분기, 화면 등을 확인해 관계/시점이 판정됨 | **그 장면·상태에 한해** 조건부 규칙으로 사용 |
| `INFERRED` | 자료를 바탕으로 한 해석이나 추측이나 반례 미검토 | 승인 전 전역 사실로 쓰지 않음 |
| `CONFLICTED` | 출처가 서로 충돌하거나 시점·루트가 구별되지 않음 | 적용 보류 및 ISSUE 등록 |

`OBSERVED`는 관찰 사실의 단정이지 사건 전체의 진실에 대한 판정이 아니다. 등장인물이 “소문이래”라고 말했다면 **그렇게 말한 사실**은 OBSERVED지만 **소문의 내용이 세계관 사실**인 것은 아니다.

### B. 번역 결정 상태 (이 한국어/목표어 표현을 사용해도 되는가?)

| 상태 | 뜻 | 사용할 때 주의 |
|---|---|---|
| `UNTRANSLATED` | 후보 문장 없음 | 번역 작업 필요 |
| `DRAFT` | 번역 후보만 있음 | 실험/교정 가능, 공식 아님 |
| `CONTEXT_REVIEW` | 화자, 상대, 시간, 분기, 의미 판정 미해결 | 확정 표현 사용 금지 |
| `LANGUAGE_REVIEW` | 의미·일관성·자연스러움 검토 중 | 승인 대기 |
| `APPROVED_TEXT` | 승인자가 특정 범위의 번역문/용어를 승인 | 그 지정 범위에서 사용 가능, 실행 시험과 별개 |
| `REJECTED` | 선택하지 않은 대안/오역 | 결정 이유를 남기고 재사용 금지 |

### C. 기술/배포 상태 (실제로 들어가서 작동하는가?)

| 상태 | 뜻 |
|---|---|
| `NOT_TESTED` | 기술적 재삽입/렌더링/재생 미실시 |
| `TECH_REVIEW` | 태그/변수/줄폭/선택지/타임코드 등 기술 쟁점 있음 |
| `RUNTIME_VERIFIED` | 실제 앱/게임/영상·빌드 조건에서 검증됨, 시험 범위 명시 |
| `RELEASE_APPROVED` | 실제 배포 승인자·범위가 명시적으로 확인됨 |

문서 생성만으로 어떤 항목도 자동 `APPROVED_TEXT`, `RUNTIME_VERIFIED`, `RELEASE_APPROVED`가 되지 않는다. 자동 검사에 성공해도 수동 맥락 판정과 운영 승인을 대체하지 않는다.

## 2. `operations/SOURCES.md` — 원본 인벤토리와 추적 가능성

```md
# Source Register

## 1. 프로젝트 소스 접근 범위
- 접근 가능한 경로와 자료 종류
- 번역 대상에 포함/제외되는 소스
- 읽지 않은 범위, 언어·버전 미확정 상태

## 2. 소스 목록
| source_id | 경로/문서 | 형식/언어 | 출처·제공자 | 버전/작성일 | 조사 범위 | 신뢰/접근 상태 |

## 3. 단위 ID 매핑 규칙
- 원본 필드/행/페이지/장면/화면/cue에서 고유 ID를 어떻게 확보하는가
- 소스 자체에 ID가 없을 때의 안정된 임시 식별법

## 4. 근거 기록 테이블
| evidence_id | source_id | unit_id/위치 | 관찰할 수 있는 내용 | 원문 직접 확인 여부 | 관련 자산 |

## 5. 인용·저작권·개인정보 유의
- 전체 원문 재복사 지양, 판단에 필요한 최소 구절과 위치만 기록

## 6. 새 버전과 누락·변경 확인
- 무엇을 다시 읽고 검증해야 하는가
```

### 단위 ID 관리

- 원본이 제공하는 안정 ID가 있으면 그 값을 보존한다.
- 없으면 **자료 경로/원본 버전/장·행/타임코드 등 재식별 가능한 구성**으로 임시 ID를 만든다. 임시 ID는 자체 생성임을 명시하고 원본 ID인 척하지 않는다.
- 근거에는 파일이 존재한다는 사실만이 아니라 실제로 열람한 범위와 내용을 함께 남긴다. `다 읽음`이라고 표시하려면 전체를 실제로 확인해야 한다.
- 동일 프로젝트 안에서 `source_id`와 `unit_id`가 충돌하면 병합하지 않고 먼저 해결한다.
- 소스 경로가 이동한 경우 이전 ID·위치·신규 경로를 매핑하여 상세 문서 링크를 깨뜨리지 않는다.

## 3. `operations/DECISIONS.md` — 공인된 표현/규칙의 결정 원장

```md
# Translation Decision Ledger

## 1. 결정의 효력과 승인 주체
- 누가 승인할 수 있는가 / 어떤 범위에서 유효한가
- 승인자가 미지정이면 이 원장에는 DRAFT/REQUESTED만 기록

## 2. 결정 인덱스
| decision_id | 대상 term/rule/unit | 요약 | 상태 | 적용 범위 | 승인 일자 | 상세 앵커 |

## 3. 개별 결정
<a id="decision-d001"></a>
### D001 — [표현/문체/구현 결정]
- 문제/배경과 원본 단위:
- 실제 관찰과 문맥:
- 선택 가능한 표현/정책 후보 1·후보 2:
- 최종 선택안:
- 선택 이유 및 반례/사용 금지 조건:
- 적용 범위(언어/버전/화자/상대/시점/문서):
- 검토자/승인자/일자: [없으면 미승인]
- 관련 근거 ID, ISSUE ID, 변경 대상 파일:
- 재검토 트리거/폐기 조건:

## 4. 변경/폐기/승계된 결정
| 이전 결정 | 후속 결정 | 변경 사유 | 영향받는 번역 단위 |
```

### 결정 관리 원칙

- `추천`과 `승인`을 같은 열에 섞지 않는다. 승인자가 없으면 `APPROVED_TEXT`로 전환하지 않는다.
- 최종 선택을 나중에 바꿨다면 원래 결정을 삭제하지 말고 새 결정과 `supersedes` 관계를 남긴다.
- 특정 관계/루트에서만 성립하는 예외를 프로젝트 전역으로 승격하지 않는다.
- 번역 엔진에서 값이 바뀌었다고 해서 번역 정책까지 자동 변경된 것으로 간주하지 않는다.

## 4. `operations/ISSUES.md` — 미확정과 실제 충돌의 대기열

```md
# Issues and Open Questions

## 1. 열려 있는 문제 요약
| issue_id | 수준 | 종류 | 영향받는 대상 | 상태 | 담당 | 상세 링크 |

## 2. 개별 이슈
<a id="issue-i001"></a>
### I001 — [해결할 질문]
- 발견 위치와 원문 단위:
- 실제 문제: [무엇이 불확정/충돌인지]
- 증거 A / 증거 B / 해석 차이:
- 영향받는 번역/화자/스토리/기술:
- 위험 수준: P0/P1/P2/P3
- 임시 조치: [안전하게 보류할 작업 범위]
- 추가 확인할 자료·테스트:
- 책임자/상태/마감(있을 때):
- 해결 기록 / 관련 decision_id:

## 3. 닫힌 이슈와 재발 조건
- 원문 근거와 승인된 결정을 남긴 뒤 상태 갱신
```

**이슈를 만드는 경우:** 같은 이름이 다른 인물을 가리킬 가능성, 특정 화자의 존대가 시점·농담에 따라 바뀌는 문제, 인명 독음 미확정, 이전 루트의 결말을 현재 루트로 도입하려는 충돌, 기술 태그 보존 실패 등. 애매하다고 무조건 선택해 확정하지 않는다.

## 5. `operations/QA_LOG.md` — 검수 결과와 실제 시험 이력

```md
# QA and Runtime Verification Log

## 1. 적용하는 QA 체크와 담당자
- 원문 의미/누락/부정·질문·수치/용어/화자/관계/기술 구조/화면

## 2. QA 작업 목록
| qa_id | unit_id 또는 범위 | 검토 분야 | 결과 | 문제 ID | 검토자 | 환경/빌드 |

## 3. 개별 언어·맥락 검수
- 비교한 원문/번역 버전, 사용한 하네스 문서/앵커
- 오류 종류·심각도, 수정 전후, 승인 또는 재검토

## 4. 기술·매체 시험 기록
- 테스트 환경(앱/게임/자막/웹), 빌드/해상도/기기·날짜
- 실제 테스트한 문자열/분기·태그·자막 범위
- 결과와 스크린샷/로그/리포트 위치(있을 때)

## 5. 미검수·재검수 대상
| 변경 출처/결정 | 영향받는 범위 | 필요 재검증 | 담당자 |
```

**실제 시험을 하지 않았다면 `RUNTIME_VERIFIED`를 쓰지 않는다.** `문서를 열어봤다`, `구조 검사가 통과했다`, `번역이 자연스럽다`는 기술 검증과 별개다.

## 6. `operations/CHANGELOG.md` — 수정 기록과 영향 분석

```md
# Harness Change History

## 변경 요약
| 변경 ID/날짜 | 변경 문서 | 이전→현재 | 원인/출처/결정 | 영향받는 문서/번역 단위 | 검증 |

## 변경 요청의 처리 순서
- 변경 발견 → 사실 재대조 → 영향 문서 탐색 → 기준 문서 수정 →
  역참조/Rule/인덱스 업데이트 → QA 재실행 → 변경 이력 기록

## 대형 변경/이관 시 주의
- 예전 승인 문구 임의 폐기 금지
- 단위 ID/앵커 유지 또는 명시적 리다이렉션
- 이전 문서의 미확정을 승인된 지식으로 옮기지 않음
```

**변경 예:** 캐릭터 독음 확정 → `GLOSSARY`의 후보/상태 수정 → `CHARACTER_BIBLE`과 해당 프로필 링크/표기 갱신 → 기존 번역에서 영향받는 단위 식별 → 결정·QA 로그 갱신. 단순 변경 한 줄이 아니라 영향 그래프를 따라 수정한다.

## 7. 원문 번역 단위의 공통 작업 기록

`PROMPT_TEMPLATE.md`의 출력 계약과 `QA_LOG.md`를 다음 **의미 필드**로 연결한다. 소스 포맷을 특정 구조로 고정하지 않는다.

```yaml
unit_id: "SOURCE-A:segment-003:line-024"  # 설명을 위한 가상 ID
source_ref: "S001"
work_type: "dialogue"                      # 또는 UI / subtitle / narration / document
original_context: "장면 범위 또는 화면 상태"
speaker_id: "C001"
addressee_id: "C002"
addressee_basis: "CONTEXT_CONFIRMED"
applicable_scope: "ARC-002 / stage-1"
read_harness_refs:
  - "guides/01_EXECUTION.md"
  - "characters/profiles/C001.md#char-c001-to-c002-stage1"
glossary_refs: ["T010"]
observed_fact: "원문에서 직접 확인한 언어 정보"
proposal: "목표 언어 번역 후보"
exceptions: "이 규칙을 적용하지 않을 다른 장면"
meaning_review: "PENDING"
technical_review: "NOT_TESTED"
text_approval: "DRAFT"
issues: ["I004"]
```

**주의:** 위는 공통 작업 기록이 어떤 정보를 연결해야 하는지 보여 주는 *가상의 예*다. 원문이 JSON/CSV/Excel/텍스트/영상 등 어떤 형식인지와는 별개다. 실제 입력/출력 파일 형식은 프로젝트에 맞춰 정의한다. 가상의 ID를 최종 자산의 실제 근거로 사용하지 않는다.

## 8. 기준 문서와 상태 승격 규칙

| 관리 객체 | 단일 기준 위치 | 다른 문서에서 하는 일 |
|---|---|---|
| 고유 용어의 확정 표기 | `glossary/GLOSSARY.md` + 결정 ID | 인물/스토리에서 용어 ID 참조 |
| 공통 번역 실행법 | `guides/01_EXECUTION.md` | 중앙 가이드에서 링크 |
| 인물의 상대별 말투 | 해당 `characters/profiles/` 상세 절 | 캐릭터 인덱스의 방향성 링크 |
| 루트·장면 공개 사실 | `story/arcs/` 및 필요 시 타임라인 | 스토리 인덱스에서 진입 |
| 제품 기능/화면의 사실 | `knowledge/topics/`, `media/` | 용어집과 정책에서 연결 |
| 승인 의사결정의 증거 | `operations/DECISIONS.md` | 각 용어/화법/번역안이 decision_id 참조 |
| 이슈 해결 과정 | `operations/ISSUES.md` | 영향받은 문서에서 issue_id 참조 |
| 원본 ID/파일 신뢰 | `operations/SOURCES.md` | 상세 문서에서 source_id/unit_id 참조 |

### 승격(프로젝트 규칙으로 확정)하기 전 검사

1. 출처 ID가 있고 실제 원문/맥락에서 해당 사실을 다시 확인했는가?
2. 적용 범위와 금지 범위가 정의되어 있는가?
3. 의미/시점/기술/목표 언어 관점에서 충돌하는 근거가 없는가?
4. 승인자/승인 일자/결정 ID가 있는가? 승인자가 없으면 후보 그대로 보유한다.
5. 기준 문서를 수정하고 인덱스·관련 문서·QA 영향 범위까지 갱신했는가?
6. 실제 매체 시험까지 했는가? 안 했다면 텍스트 승인과 런타임 검증을 구분한다.

**최상위 원칙:** 구조적 완성도는 지식의 진실성을 증명하지 않는다. 원본 관찰은 번역 제안을 자동 승인하지 않고, 번역 승인은 실행 검증을 자동 승인하지 않는다.
